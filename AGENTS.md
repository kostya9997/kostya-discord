# Инструкция для ИИ-агентов и разработчиков: Версионирование и история изменений

Данный документ является **обязательным стандартом** для всех ИИ-агентов и разработчиков, работающих над кодовой базой **Discord P2P Call**.

---

## 1. Специфика проекта (P2P-архитектура)

Приложение работает по модели **Peer-to-Peer (WebRTC)** без постоянного центрального сервера базы данных. Связь между двумя пользователями осуществляется через обмен SDP-токенами и WebRTC DataChannel.

> **КРИТИЧЕСКИ ВАЖНО:**  
> Клиенты собеседников (Пир А и Пир Б) должны быть совместимы по протоколу передачи данных. Если один из собеседников открыл старую версию страницы из кэша, а второй — новую с измененным протоколом сжатия SDP или структурой чанков файлов, звонок может не состояться.
> Поэтому в коде реализована сверка версий: при подключении клиенты обмениваются `version` и предупреждают о несовпадении (`version-mismatch`).

## 2. Где в коде задается версия (Обязательная синхронизация)

В начале файла `script.js` заданы константы:

```javascript
// === КОНФИГУРАЦИЯ И ВЕРСИОНИРОВАНИЕ ПРИЛОЖЕНИЯ ===
const APP_VERSION = '1.2.0';
const APP_BUILD_DATE = '24.10.2026';
const APP_BUILD_ID = '20261024-r3';
```

### Правило агента:
При внедрении изменений, требующих обновления версии:
1. Обновите `APP_VERSION` по правилам SemVer (см. раздел 3).
2. Обновите `APP_BUILD_DATE` на текущую дату (формат: `ДД.ММ.ГГГГ`).
3. Инкрементируйте или обновите идентификатор сборки `APP_BUILD_ID` (формат: `ГГГГММДД-r<номер>`).
4. Убедитесь, что функция `initVersioningUI()` корректно связывает эти значения с интерфейсом.

## 3. Семантическое версионирование (SemVer: `MAJOR.MINOR.PATCH`)

* **MAJOR (1.x.x -> 2.0.0)** — **Несовместимые изменения протокола P2P**:
  * Изменение алгоритма сжатия или формата SDP-токена (старый клиент не сможет прочитать новый код).
  * Изменение формата передачи сообщений или чанков файлов по DataChannel (`p2p-chat-msg`, `file-chunk`).
  * Требует обязательного обновления обоими участниками звонка (Ctrl+F5).

* **MINOR (1.2.x -> 1.3.0)** — **Новый функционал с сохранением обратной совместимости**:
  * Новые аватары, элементы гардероба, инструменты доски (Whiteboard).
  * Новые локальные настройки звука/видео, пресеты демонстрации экрана.
  * Новые визуальные виджеты, не ломающие базовый обмен данными со старой версией.

* **PATCH (1.2.0 -> 1.2.1)** — **Багфиксы и оптимизации**:
  * Исправление визуальных багов в CSS, стилей Discord.
  * Оптимизация производительности (canvas, audio context).
  * Исправление утечек памяти или опечаток в интерфейсе.

## 4. Стандарт коммитов (Conventional Commits)

В истории репозитория **не должно быть** мусорных сообщений вроде `fix`, `wip`, `update`, `123`, `test`.  
Любой коммит в ветку `main` должен начинаться с одного из префиксов:

| Префикс | Назначение | Пример |
| :--- | :--- | :--- |
| `feat:` | Новая функциональность | `feat: добавлен ластик на интерактивную доску` |
| `fix:` | Исправление бага | `fix: устранен сброс звука при повторном шаринге экрана` |
| `p2p:` | Правки P2P протокола и WebRTC | `p2p: оптимизирован размер чанков DataChannel` |
| `ui:` | Изменения интерфейса и CSS | `ui: обновлены кнопки гардероба в стиле Discord` |
| `perf:` | Оптимизация производительности | `perf: сглаживание анимации рта аватара на 60fps` |
| `refactor:` | Рефакторинг кода без смены логики | `refactor: вынесена логика Web Audio в отдельный модуль` |
| `chore:` | Вспомогательные задачи | `chore: обновление инструкций и release.yml` |

### Требование к атомарности:
* Если агент или разработчик тестирует несколько правок локально — перед фиксацией изменений в `main` объединяйте их в один чистый коммит или используйте **Squash and Merge** в Pull Request.

## 5. Ведение `CHANGELOG.md`

Файл `CHANGELOG.md` ведется по стандарту **Keep a Changelog**:

1. **Во время разработки:**
   * Все новые изменения сразу дописываются в раздел `## [Unreleased]`.
   * Используются категории: `### Добавлено`, `### Изменено`, `### Исправлено`.
2. **В момент релиза версии:**
   * Заголовок `## [Unreleased]` превращается в `## [X.Y.Z] - ГГГГ-ММ-ДД`.
   * Выше создается новый пустой блок `## [Unreleased]`.

## 6. Публикация релиза на GitHub

Для удобного отображения истории версий в GitHub настроен файл конфигурации `.github/release.yml`.

### Шаги при выпуске новой версии:
1. Убедиться, что `script.js` (`APP_VERSION`), `CHANGELOG.md` и код синхронизированы.
2. Закоммитить изменения:
   ```bash
   git commit -m "chore: подготовка релиза v1.3.0"
   ```
3. Создать Git-тег:
   ```bash
   git tag -a v1.3.0 -m "Релиз v1.3.0"
   git push origin main --tags
   ```
4. В веб-интерфейсе GitHub (вкладка **Releases** -> **Draft a new release**):
   * Выбрать созданный тег `v1.3.0`.
   * Нажать кнопку **«Generate release notes»**.
   * GitHub автоматически распределит коммиты по категориям на основе `.github/release.yml` и исключит мусор.
   * В самое начало описания добавить 1-2 предложения человеческим языком: суть релиза («Что нового для пользователей звонка»).
   * Опубликовать релиз (**Publish release**).

## 7. Отображение версии внутри приложения («О версии»)

В интерфейсе приложения пользователю доступны:
1. **Бейджи версии** (`#app-version-badge`, `#lobby-version-badge`) — показывают текущую активную сборку.
2. **Индикатор версии пира** (`#metric-peer-version`) в панели разработчика — подсвечивает зеленым совпадение версий и красным (`version-mismatch`) несовпадение.
3. **Модальное окно информации** (`#version-modal`) — отображает дату сборки, ID сборки и кнопку принудительного обновления кэша (`#force-reload-btn`), которая перезагружает страницу с параметром сброса кэша браузера `?v=<timestamp>`.

При любых доработках UI версионирования сохраняйте эти идентификаторы и привязки.
